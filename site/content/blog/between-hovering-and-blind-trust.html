If you stand over a carpentry apprentice's shoulder watching every tap of the mallet, you might as well drive the chisel yourself. Your neck aches, your focus drifts, and you end up nodding without looking.

Yet if you hand that apprentice your workshop keys, leave town for a month, and set zero check-in dates, you take a reckless gamble. You return to ruined walnut boards, dull tools, and an empty bank account.

Skilled trades avoid both traps by using milestone checkpoints. The apprentice marks the cut lines, you check the dimensions against the blueprint, they rough out the joinery, and you inspect the dry fit before any glue touches the wood.

Software agents need the same middle ground. Today, most assistants force people to choose between hovering over hundreds of confirmation dialogs or turning their backs and praying nothing breaks.

What 695 real-world failures teach us

When software agents fail in everyday use, where does the fault lie? Is the language model simply not smart enough, or is the way we configure its autonomy broken?

A research team at Carnegie Mellon University set out to answer that question by studying 695 real-world failure incidents across public repositories.1 The authors examined cases where agents wrote code, manipulated user interfaces, and conducted online transactions on behalf of users.1

They identified twelve distinct failure modes across three interaction stages: before action begins, during execution, and after completion.1 Their central finding was striking: the exact same model running the exact same task failed in different ways depending on how much autonomy the system allowed between user check-ins.1

Autonomy is not an abstract personality trait of an AI model. Autonomy is a design setting chosen at deployment time. It dictates how many actions an assistant may take before it must stop and check back with a human.

When developers build an assistant without intermediate stopping points, they trap users on one side of a steep cliff. Either the person watches every command, or the person abdicates responsibility completely.

The hovering trap and approval fatigue

The first trap looks safe on paper. To prevent mistakes, the developer programs the assistant to ask for confirmation before calling any tool.

The user starts their morning by asking the assistant to clean up project dependencies. Within thirty seconds, the screen fills with prompts. Can I read package.json? Can I run npm audit? Can I inspect the lockfile? Can I check this Git branch?

Human attention does not work like a mechanical switch. Decades of ergonomics research show that frequent, low-stakes confirmation dialogs produce habituation.2 When people face dozens of interruptions an hour, their brains treat the prompt as friction to dismiss rather than a decision to evaluate.

Users begin clicking "Allow" on reflex. At that point, the safety check has evaporated. The system annoys the user all day while still allowing a destructive deletion to slip through unnoticed during an afternoon lapse of focus.

The blind trust trap and compounding drift

Frustrated by constant interruptions, teams often swing to the opposite extreme. They give the assistant a broad prompt, grant it full terminal access, and walk away to brew tea.

This triggers the blind trust trap. Language models are probabilistic pattern matchers, not psychic mind-readers. When an instruction contains a slight ambiguity, the model picks a plausible interpretation and proceeds.

In a long, unmonitored execution chain, early errors compound. At step three, the agent mistakes a test database for a scratch file. At step seven, it runs a migration that overwrites user tables. By step twenty, it has committed changes, deployed to staging, and sent status emails.

When the user returns, they face an expensive disaster. Untangling twenty dependent actions across multiple tools takes far longer than writing the code manually from scratch. The user loses confidence and abandons the tool entirely.

The silent approval gap

Between hovering and blind trust lies a third failure mode that appears across modular agent architectures. Most modern assistants split tasks between a desktop host application and separate tool servers that handle shell commands or database updates.

This division creates a dangerous coordination gap. Developers building tool servers assume the host interface prompts the person before running dangerous commands. At the same time, developers building host interfaces assume the tool server protects itself.

Because each side assumes the other checks for consent, neither side asks. A security audit of one thousand tool repositories by Yao et al. revealed that ninety percent of destructive tools provide no server confirmation.5 Across forty-one popular agent hosts, thirty-two run tools without confirmation by default.5

When researchers tested destructive tool calls across common host and tool pairings, over sixty percent ran without any human confirmation.5 In test runs with low-cost models, prompt injections triggered hundreds of unapproved file deletions.5 Both sides believed protections were active, yet the command executed silently.

Designing milestone checkpoints and authority leases

Reliable teamwork does not require watching every breath or vanishing until Friday. It requires structured milestones. In software delegation, this principle translates into three concrete mechanisms.

First, bounded authority leases. Instead of giving an assistant open-ended access to an entire workspace, give it an expiring lease for a single stage. For instance, permit it to inspect files and draft an outline, but require a new lease before it modifies code.

Second, structured action receipts. When reaching a milestone, the assistant must stop and display a plain receipt. That receipt shows three facts: what external sources it read, what changes it prepared, and what it intends to do next.

Third, five-second inspectability. A human cannot audit a wall of raw JSON logs during a busy workday. The receipt must summarize boundary crossings clearly: files touched, network endpoints queried, and credentials used.

With those three pieces in place, the relationship shifts from an adversarial tug-of-war into a calm rhythm. The assistant works independently on focused chunks, while the human provides strategic steering without suffering from cognitive overload.

Closing the approval gap requires applying the security principle of fail-safe defaults. The host application must assume every tool call is dangerous unless that tool carries an audited read-only tag. Yao et al. found that when hosts prompt for every tool without a read-only tag, the share of unconfirmed destructive pairings drops from sixty percent to five percent.5

Combining fail-safe defaults with milestone checkpoints gives users safety without approval fatigue. The assistant reads documents, searches code, and gathers context without interruptions. When the plan calls for modifying files or dropping database records, the system pauses at a clear checkpoint and asks for review.

For researchers and systems architects

This design pattern builds on foundational work in human-automation interaction and security. Parasuraman, Sheridan, and Wickens established ten distinct levels of automation, demonstrating that intermediate levels (where automation executes suggestions only after consent or provides veto windows) dramatically outperform fully manual or fully autonomous extremes.3 Amershi et al. formalized these trade-offs in the Microsoft Guidelines for Human-AI Interaction.4 They focused on three rules in particular: Guideline 1 for clear capability bounds, Guideline 9 for prompt fatigue mitigation, and Guideline 10 for scoping authority during ambiguous requests.4

In our architecture, these insights combine with Object-Capability (OCap) patterns, fail-safe defaults (Saltzer & Schroeder, 1975), and authority leases. Rather than granting ambient permissions, the host sandbox issues short-lived capability tokens that expire upon reaching a defined milestone state. The agent emits a tamper-evident action receipt signed with its session key, proving what resources were accessed before the host releases the next capability lease. Where checkpoints fall short

Milestone checkpoints do not solve every delegation challenge. If developers design milestones that are too wide, the compounding drift problem reappears inside each stage. If they design milestones that are too narrow, the prompt fatigue problem returns under a different name.

Finding the natural seams of a task requires thoughtful system design. A good milestone matches the points where a human craftsperson would naturally pause to check their work: after drafting a plan, after assembling components, or before pushing changes to shared systems.

Checkpoints also fail if the software produces cluttered, dishonest receipts. If an assistant hides a questionable database query beneath fifty lines of self-congratulatory prose, the user cannot make an informed judgment. Receipts must remain concise, factual, and focused on boundaries.

Even with these caveats, intermediate milestones offer the only sustainable path forward. We do not need assistants that demand our attention every ten seconds, nor do we need black boxes running wild in our systems. By building clear checkpoints and expiring leases, we keep people in control of the tools that serve them.
