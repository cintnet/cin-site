When an automated assistant operates on its own, testing whether it follows instructions looks straightforward. You test whether the prompt denies unauthorized commands, check the outgoing message against safety filters, and inspect the response before sending it. In a demo with one user and one task, this setup often works well.

That simple picture breaks down as soon as multiple assistants run at the same time. In public agencies, hospitals, and municipal offices, dozens of automated workflows read and update the same databases simultaneously. When each assistant checks only its own prompt rules, the system develops race conditions, double allocations, and budget overruns.

Safety cannot live inside the language model alone. If the underlying data store lacks transactional locks and external state governance, valid individual decisions can combine into an administrative disaster.

The concert ticket problem

Imagine a small theatre selling tickets for an evening show. Two ticket sellers stand at separate windows, each holding a blank notebook. A customer walks up to the first window and asks for front-row seat four. The seller checks their own notebook, sees no record for seat four, and takes the payment.

At the exact same second, another customer approaches the second window and asks for the same seat. The second seller checks their blank notebook, confirms the seat looks open, and takes the payment. Both sellers followed their instructions perfectly. Neither made an error. Yet two families now hold tickets for the exact same seat.

In traditional software, engineers solved this problem decades ago through database transactions. Before a seller can write to the ledger, the database places a lock on seat four. The second seller must wait until the first sale finishes or aborts. The transaction completes cleanly, the lock releases, and the second customer gets a prompt notice that the seat is taken.1

Why stateless prompt guards fail in the wild

Many modern agent platforms forget this hard-won lesson. They wrap each assistant in extensive prompt instructions, guardrails, and output classification filters. These safeguards inspect each incoming command and outgoing tool call in isolation, asking whether the request seems polite, helpful, and within scope.

What an isolated prompt check cannot see is what another assistant is doing three milliseconds away. Consider a municipal housing fund with a remaining balance of ten thousand dollars. Assistant A receives an emergency grant application for eight thousand dollars and verifies the applicant qualifies. Assistant B receives a separate application for seven thousand dollars and verifies that applicant qualifies too.

Both assistants read the available balance as ten thousand dollars. Both safety filters confirm that eight thousand and seven thousand are each below the ten-thousand-dollar ceiling. Both assistants fire their disbursement tools simultaneously. The municipal bank account overdraws by five thousand dollars. Researchers studying agent governance call this stale authorization: the approval was correct when given and wrong by the time the money moved.2

No prompt engineering fixes this failure mode. The failure happened in the gap between reading the shared state and committing the external effect.

What stateful governance adds

To make concurrent assistants safe, organizations need an external stateful governance proxy. This proxy sits outside the language model and mediates every tool execution that reads or alters shared resources. It brings three classic database guarantees into agent architectures.

First, it enforces strict concurrency control. When an assistant attempts an irreversible action, such as spending funds or changing a legal status, the proxy acquires an explicit lock on the affected records. Competing actions must wait in an orderly queue until the first transaction completes.

Second, it verifies state serializability before committing external effects. The proxy checks that the facts the assistant relied on when planning its action remain true at the moment of execution. If another process modified the budget balance in the meantime, the proxy aborts the transaction safely.

Third, it provides automated rollbacks and signed transaction receipts. When a multi-step workflow fails midway through execution, the proxy rolls back partial updates to restore the agency ledger to a known clean state. It hands the user and the administrator an auditable receipt proving who acted and what changed.

What public agencies should require

Public procurement rules for artificial intelligence often focus on model benchmarks and ethics guidelines. While responsible guidelines matter, they cannot replace rigorous operational safeguards. Public officials buying or building agentic systems should require three concrete technical commitments from vendors.

Tenders should mandate external stateful proxies for all consequential tool calls, forbidding systems that rely solely on prompt-based self-policing. Contracts should require explicit transaction isolation levels, so that concurrent automated processes do not corrupt shared public registries or overspend communal budgets. Finally, agencies should require verifiable transaction receipts saved to independent storage. The Council of Europe's AI convention already asks states to keep AI systems accountable and open to oversight; these commitments are one practical way to do that.3

Software that serves the public must handle the rush of everyday civic life without collapsing under simultaneous demands. Grounding automated agents in stateful transaction locks helps our institutions stay steady, predictable, and fair.

For researchers

In distributed database theory, concurrent execution is correct if and only if it is equivalent to some serial execution (serializability), the standard correctness condition for databases; Berenson et al. show how the common isolation levels fall short of it.1 Peng and Wu carry the idea to agents as policy-state serializability: each committed effect must be explainable as authorized against the policy state immediately before it happens. Their MasuGate prototype prevented stale authorizations that baselines passing policy state as request context missed.2
